# Деплой на Timeweb Cloud (облачный сервер + Docker Compose)

Весь стек живёт на **одном облачном сервере**: `docker compose up -d` поднимает
`postgres`, `redis`, `api`, `bot`, `frontend` и `nginx`, наружу открыты только
`:80` и `:443` у nginx. TLS выписывает certbot в отдельном контейнере.

Отличие от Railway: там каждый сервис был отдельным приложением со своим
домена и своей приватной сетью, а фото лежали в платформенном volume. Здесь
всё в одной docker-сети на одной машине, фото — в docker-томе `media_players`,
база — в томе `postgres_data`. Прикладной код при этом **не меняется**: и на
Railway, и здесь фронтенд и API отдаются с одного домена, поэтому куки сессии
остаются first-party и вход в админку работает как раньше.

| Что | Где | Чем задаётся |
|---|---|---|
| Сайт и админка | `frontend` (Next.js), за nginx | `docker-compose.yml` |
| API сайта и бота | `api` (FastAPI) | `docker-compose.yml` |
| Telegram-бот | `bot`, порта не слушает | `docker-compose.yml` |
| База и Redis | `postgres`, `redis`, тома на диске сервера | `docker-compose.yml` |
| TLS и маршрутизация | `nginx` + `certbot` | `docker-compose.prod.yml`, `nginx/nginx-tls.conf` |

`docker-compose.prod.yml` — надстройка над базовым файлом: она включает TLS,
добавляет certbot и подставляет домен в `NEXT_PUBLIC_SITE_URL` и
`CORS_ORIGINS`. Подключать её флагами `-f` не нужно: в корневом `.env` стоит
`COMPOSE_FILE=docker-compose.yml:docker-compose.prod.yml`, и любая команда
`docker compose` в этом каталоге читает оба файла. Локально корневого `.env`
нет — читается только базовый файл, сайт поднимается по http (см.
[README.md](README.md)).

## 1. Сервер и домен

**Сервер.** Timeweb Cloud → Облачные серверы → Создать. Хватает конфигурации
**2 vCPU / 4 ГБ RAM / 40+ ГБ NVMe**, ОС **Ubuntu 24.04**. Меньше 4 ГБ брать не
стоит: сборка образа фронтенда (`npm run build`) — самая тяжёлая операция на
этой машине, и на 2 ГБ она падает по памяти.

**Домен.** `cmcmafia.ru` зарегистрирован. Осталось направить его на сервер:
Timeweb Cloud → Домены → `cmcmafia.ru` → DNS-записи, создать **A-запись**
`@` → IP сервера. Запись `www` — по желанию, но если её заводить, то **до**
выпуска сертификата: скрипт `init-tls.sh` смотрит, резолвится ли `www`, и
включает его в сертификат. Добавить www позже — значит перевыпускать
сертификат. Сам сайт в любом случае живёт на голом домене: nginx редиректит
`www.cmcmafia.ru` на `cmcmafia.ru`, чтобы origin (а значит и куки сессии) был
один.

Проверять, пока не ответит:

```bash
dig +short cmcmafia.ru      # должен вернуть IP сервера
dig +short cmcmafia.ru NS   # NS Timeweb -- признак, что домен делегирован
```

Сразу после покупки домен обычно ещё не делегирован (обе команды молчат) —
это нормально, делегирование занимает от пары часов до суток. Пока первая
команда не вернёт IP сервера, **сертификат выпустить не получится**: Let's
Encrypt проверяет домен обращением по HTTP именно на этот адрес, и каждая
неудачная попытка тратит квоту (5 отказов в час на домен).

## 2. Подготовка сервера

Всю подготовку машины делает [deploy/cloud-init.sh](deploy/cloud-init.sh).
Содержимое файла **вставляется в поле Cloud-init** при создании сервера в
панели Timeweb — тогда к моменту, когда сервер поднимется, всё уже готово и
подключаться по SSH нужно только чтобы заполнить секреты.

Если сервер уже создан, тот же скрипт запускается руками (репозиторий
публичный, никаких ключей не нужно):

```bash
curl -fsSLO https://raw.githubusercontent.com/kobylinskii/cmcmafia/master/deploy/cloud-init.sh
bash cloud-init.sh
```

Скачать и запустить отдельной командой надёжнее, чем `curl | sh`: оборванная
закачка в пайпе выполнится наполовину и молча.

Что он делает:

- ставит Docker с официального репозитория — не `docker.io` из репозитория
  Ubuntu, там старее и без плагина `docker compose`;
- переносит SSH на порт из переменной `SSH_PORT` (по умолчанию **2222**),
  оставляет вход только по ключу и открывает в `ufw` этот порт, 80 и 443 —
  ни база, ни api, ни фронтенд портов наружу не пробрасывают;
- добавляет 4 ГБ swap со `swappiness=10`: самая тяжёлая операция на этой
  машине — `npm run build` фронтенда, и упирается она именно в память;
- включает автоматические обновления безопасности — после ухода с управляемой
  платформы патчи ОС стали вашей заботой;
- клонирует репозиторий в `/opt/cmcmafia`, создаёт три `.env` из примеров,
  генерирует `POSTGRES_PASSWORD` и закрывает файлы правами `600`;
- кладёт памятку в `/root/next-steps.txt` и показывает её при входе по SSH.

Лог работы — `/var/log/cmcmafia-init.log`. Повторный запуск безопасен:
заполненные `.env` не затираются, swap и клон не дублируются.

> **Про порт SSH.** 22-й наружу — это непрерывный перебор паролей ботами с
> первых минут жизни публичного адреса: на нашем сервере за восемь часов
> набежало 4758 попыток. На нестандартном порту он прекращается полностью.
> В файрволе открывается только новый порт: правило для 22-го, на котором
> sshd уже не слушает, не защищает ни от чего — оно лишь держит дырку.
> Скрипт сначала переносит sshd и проверяет, что тот действительно слушает
> новый порт, и только потом включает ufw. Вернуть привычный порт:
> `SSH_PORT=22 bash cloud-init.sh`.

> **Секретов в cloud-init быть не должно.** Его содержимое хранится у
> провайдера и доступно изнутри машины через сервис метаданных любому
> процессу. Поэтому `JWT_SECRET`, `BOT_TOKEN` и прочее заполняются руками
> после подключения по SSH, а не вписываются в скрипт.

Три файла `.env`, у каждого своя роль:

- **`.env`** (корень) — то, что читает сам `docker compose`: домен, пароль
  Postgres, подключение продакшн-надстройки.
- **`backend/.env`** — настройки API. `DATABASE_URL`, `REDIS_URL`,
  `COOKIE_SECURE` и `CORS_ORIGINS` оттуда **перекрываются** compose-файлами
  (внутри docker-сети адреса — это имена сервисов, а домен берётся из `.env`),
  править их там не нужно.
- **`bot/.env`** — токен бота. `API_BASE_URL` и `REDIS_URL` тоже перекрываются
  compose.

`POSTGRES_PASSWORD` скрипт уже сгенерировал. Если ставите с нуля, а не
переезжаете, остальные два секрета — так:

```bash
openssl rand -hex 32   # -> JWT_SECRET в backend/.env
openssl rand -hex 32   # -> BOT_SERVICE_TOKEN, ОДНО И ТО ЖЕ значение в backend/.env и bot/.env
```

**Если переносите существующий сайт с Railway — возьмите старые значения
`JWT_SECRET` и `BOT_SERVICE_TOKEN` из переменных сервисов Railway, а не
генерируйте новые.** Новый `JWT_SECRET` разлогинит всех админов (не страшно),
а вот рассинхрон `BOT_SERVICE_TOKEN` между `api` и `bot` — это молча
переставший работать бот.

Заполнить в `.env`:

| Переменная | Значение |
|---|---|
| `DOMAIN` | `cmcmafia.ru` — без схемы и без `www` |
| `LETSENCRYPT_EMAIL` | адрес для писем о протухающем сертификате |
| `POSTGRES_PASSWORD` | уже сгенерирован скриптом. Менять после первого запуска нельзя: том базы создан с этим паролем |
| `COOKIE_SECURE` | `true` |
| `NEXT_PUBLIC_BOT_USERNAME` | username бота без `@` |

В `backend/.env`: `JWT_SECRET`, `BOT_SERVICE_TOKEN`,
`SUPERADMIN_TELEGRAM_IDS_RAW`, `BOOTSTRAP_ADMIN_PHONE_RAW`,
`MEDIA_ROOT=./media/players`, `COOKIE_SAMESITE=lax`.
В `bot/.env`: `BOT_TOKEN` и тот же `BOT_SERVICE_TOKEN`.

## 3. Первый запуск и сертификат

Собрать образы (фронтенд собирается минуты, бэкенду живая база на сборке не
нужна):

```bash
docker compose build
```

Выпустить сертификат — этот скрипт заодно поднимает весь стек:

```bash
./deploy/init-tls.sh
```

Что он делает: кладёт самоподписанную заглушку (без файла сертификата nginx
вообще не стартует), поднимает стек, проверяет, что nginx отдаёт файлы
ACME-проверки, убирает заглушку, просит настоящий сертификат и перечитывает
конфиг. Запускается **один раз**.

Поставить продление в крон root'а (`crontab -e`):

```
0 4 * * 1 /opt/cmcmafia/deploy/renew-tls.sh >> /var/log/cmcmafia-tls.log 2>&1
```

Проверить:

```bash
curl -I https://cmcmafia.ru/mafia        # 200, есть Strict-Transport-Security
curl -I http://cmcmafia.ru/mafia         # 301 на https
curl -s https://cmcmafia.ru/api/rating   # JSON рейтинга
docker compose ps                       # api -- healthy
docker compose logs bot | tail          # Start polling
```

`/health` наружу не выставлен намеренно: этот путь уходит во фронтенд, а
healthcheck дёргает его внутри контейнера api. Признак живого бэкенда снаружи —
любой публичный путь под `/api/` (список их всех — ARCHITECTURE.md, раздел 4).

## 4. Перенос базы и фото с Railway

Делать **до** переключения DNS и **до** погашения Railway: фото тянутся по
HTTP с ещё живого старого сайта — том с ними снаружи недоступен.

Понадобятся два адреса из Railway: у сервиса Postgres переменная
`DATABASE_PUBLIC_URL` (та, что с `*.proxy.rlwy.net`; внутренний
`*.railway.internal` снаружи не резолвится) и текущий публичный адрес сайта.

**Если `DATABASE_PUBLIC_URL` в списке переменных нет** — у сервиса не включён
публичный доступ, и базы Railway по умолчанию видны только изнутри своей сети.
Включается так: сервис Postgres → **Settings** → **Networking** → **TCP
Proxy** → внутренний порт **5432**. Railway выдаст домен и внешний порт, после
чего появятся `RAILWAY_TCP_PROXY_DOMAIN`, `RAILWAY_TCP_PROXY_PORT` и сам
`DATABASE_PUBLIC_URL`.

Значения на вкладке Variables показываются **ссылками** вида `${{PGPASSWORD}}`
— это шаблон, который раскрывается только внутри Railway. Готовую строку берите
на вкладке **Connect**, раздел Public Network, либо соберите из значений
отдельных переменных.

> После переноса публичный доступ к базе стоит выключить там же — или просто
> удалить проект, когда переезд признан удавшимся. Открытый в интернет Postgres
> с парольным входом живёт под тем же перебором, что и SSH на 22-м порту.

```bash
cd /opt/cmcmafia
RAILWAY_DATABASE_URL='postgresql://postgres:...@xxx.proxy.rlwy.net:12345/railway' \
OLD_SITE_URL='https://web-production-xxxx.up.railway.app' \
./deploy/migrate-from-railway.sh
```

Скрипт снимает дамп, гасит `api` и `bot` (иначе `pg_restore --clean` не
удалит объекты, за которые держится открытое соединение), восстанавливает базу
и докачивает файлы фото в том `media_players`. Список фото берётся из
восстановленной базы — включая ещё не одобренные правки фото, их файлы тоже
нужны. Повторный запуск безопасен.

Затем поднять всё обратно:

```bash
docker compose up -d
```

`api` на старте сам прогоняет `alembic upgrade head`; на восстановленной базе
это либо no-op, либо доводит схему до актуальной ревизии.

Проверить, что данные на месте:

```bash
curl -s https://cmcmafia.ru/api/rating | head -c 300
docker compose exec api ls /app/media/players | wc -l
```

Число файлов должно совпадать с числом игроков с фото:

```bash
docker compose exec -T postgres psql -U postgres -d mafia -Atc \
  "select count(*) from players where photo_url is not null"
```

> Если версия Postgres на Railway старше или новее 16, `pg_dump` откажется
> работать (клиент и сервер должны совпадать по major-версии). Скрипт печатает
> версию сервера первым делом: при расхождении поднять `image: postgres:NN` у
> сервиса `postgres` в `docker-compose.yml` и передать `PG_IMAGE=postgres:NN`
> скрипту.

## 5. Первый администратор сайта

Нужен только если начинаете с чистой базы (при переносе с Railway админы уже
внутри дампа). Эндпоинта регистрации нет намеренно — только CLI:

```bash
docker compose exec api python -m app.scripts.create_admin --nickname "Админ"
```

Скрипт печатает логин и временный пароль. Вход — `https://cmcmafia.ru/mafia/admin/login`.

## 6. Переключение DNS и выключение Railway

1. Проверить новый сайт по его домену целиком: главная, рейтинг, страница
   игрока с фото, вход в админку, ответ бота на `/start`.
2. У бота **один** `BOT_TOKEN` на оба стека, и long polling не терпит двух
   читателей: пока на Railway жив сервис `bot`, оба бота будут выхватывать
   апдейты друг у друга. Перед проверкой бота на новом сервере **остановить
   сервис `bot` на Railway** (Railway → сервис `bot` → Remove/Pause).
3. Переключить A-запись домена на IP нового сервера (если домен раньше вёл на
   Railway). Дождаться, пока `dig +short cmcmafia.ru` вернёт новый IP.
4. Дать сайту поработать сутки-двое, потом удалить проект на Railway.
   `RAILWAY.md` и файлы `*/railway.json` пока оставлены в репозитории — это
   путь отката; удалять их стоит после того, как переезд признан удавшимся.

## 7. Эксплуатация

**Обновление кода:**

```bash
cd /opt/cmcmafia && git pull
docker compose up -d --build
```

Пересборка фронтенда обязательна при смене любой `NEXT_PUBLIC_*` или домена —
эти значения вшиваются в бандл на этапе сборки, рестарта контейнера мало.

**Логи:**

```bash
docker compose logs -f --tail=100 api
docker compose logs -f --tail=100 bot
```

Драйвер логов ограничен (3 файла по 10 МБ на сервис), диск ими не забьётся.

**Бэкапы.** Это главное, что теряется при уходе с Railway: там база была
управляемой и бэкапилась платформой, здесь она живёт в docker-томе на этом
диске. Минимум — ночной дамп в файл (крон root'а):

```
30 3 * * * cd /opt/cmcmafia && docker compose exec -T postgres pg_dump -U postgres -Fc mafia > /var/backups/mafia-$(date +\%u).dump
```

Семь файлов по дням недели, перезаписываются по кругу. Фото лежат в томе
`media_players` — их стоит забирать туда же:

```
45 3 * * * tar -czf /var/backups/media-$(date +\%u).tgz -C /var/lib/docker/volumes/cmcmafia_media_players/_data .
```

Отдельно включить снапшоты диска в панели Timeweb: дамп на том же диске не
спасает от смерти диска.

**Восстановление из дампа:**

```bash
docker compose stop api bot
docker compose exec -T postgres pg_restore --clean --if-exists -U postgres -d mafia < /var/backups/mafia-3.dump
docker compose up -d
```
